# meta-oeros — Edge AI for ROS 2 on Wrynose/Lyrical

Adapted from the `oeros-edgeai-setup.json` bitbake-setup draft for Yocto
**wrynose** / ROS 2 **lyrical**. Each vendor has its own bitbake-setup
configuration (see "Configurations" below).

> **This branch is `feature/edgeai-v3`**, forked from
> `feature/edgeai-intel-robotics-ai-suite`. It adds AMD/Xilinx Kria and
> Versal (`docs/amd-xilinx.md`), splits the single lyrical config into one
> config per vendor, makes every vendor's proprietary stack an explicit
> opt-in, and fixes package and layer names that could not resolve.

> **This branch is `feature/edgeai-intel-robotics-ai-suite`, built on top of
> `feature/edgeai`.** It adds the Intel Robotics AI Suite (see the dedicated
> section below) via a **second, separate registry config**,
> `conf/registry/configurations/oeros-wrynose-jazzy.conf.json` — the suite
> forced a fork to ROS 2 Jazzy, which cannot share `bb-layers` with the
> lyrical config (see "Why a separate Jazzy config" below).

## Layout

```
meta-oeros/
├── conf/layer.conf                                  # BBFILES_DYNAMIC keyed on vendor BBFILE_COLLECTIONS
├── conf/machine/include/oeros-edgeai-<vendor>.inc    # sets OEROS_EDGEAI_VENDOR + MACHINE_FEATURES
├── conf/fragments/                                 # referenced as oeros/<name> (flat directory)
│   ├── edgeai.conf                                   # DISTRO_FEATURES += edgeai, IMAGE_INSTALL += packagegroup-oeros-edgeai
│   ├── ros-lyrical.conf                              # ROS_DISTRO = lyrical
│   ├── machine-<board>.conf                          # MACHINE=<board>; requires the vendor .inc + the two fragments above
│   └── <vendor>-proprietary.conf                     # the opt-in for that vendor's proprietary stack
├── conf/registry/configurations/
│   └── oeros-wrynose-lyrical[-<vendor>].conf.json    # generated by scripts/gen-registry-configs.py
├── recipes-core/packagegroups/
│   ├── packagegroup-oeros-edgeai.bb                  # selector: core + ros + vendor (via OEROS_EDGEAI_VENDOR)
│   └── packagegroup-oeros-edgeai-core.bb             # onnxruntime, tflite, opencv, gstreamer, python
├── recipes-ros/packagegroups/
│   └── packagegroup-oeros-edgeai-ros.bb              # vision_msgs, cv_bridge, image_transport, inference node
├── dynamic-layers/openvino/recipes-robotics-ai-suite/  # Intel Robotics AI Suite recipes, only parsed with meta-openvino (Jazzy config)
├── recipes-kria-apps/                             # AMD Kria robotics apps + KV260 camera (docs/amd-xilinx.md)
├── dynamic-layers/meta-onnxruntime/               # onnxruntime bbappend: onnxruntime-tools sub-package
└── dynamic-layers/<vendor>/recipes-core/packagegroups/
    └── packagegroup-oeros-edgeai-<vendor>.bb         # only parsed when the vendor layer is in BBLAYERS
```

## Configurations

`bitbake-setup` has no `extends`; every source in a config file is fetched
and `bb-layers` is shared by every machine option in it. So each vendor
gets its own config, generated from one shared layer list by
`scripts/gen-registry-configs.py` (run it after editing; `--check` reports
drift):

| Config | Machines | Vendor layers (on top of the common set) |
|---|---|---|
| `oeros-wrynose-lyrical` | qemu*, generic*, Raspberry Pi | meta-raspberrypi |
| `oeros-wrynose-lyrical-nvidia` | Jetson Orin Nano, AGX Orin | meta-tegra, meta-tegra-community |
| `oeros-wrynose-lyrical-nxp` | i.MX 8M Plus, 93, 95 EVKs | meta-freescale, meta-freescale-distro, meta-freescale-ml, meta-yocto/meta-poky, meta-imx (bsp, sdk, ml) |
| `oeros-wrynose-lyrical-qualcomm` | RB3 Gen 2, QCS9100 Ride SX | meta-ai, meta-qcom, meta-qcom-distro, meta-lts-mixins (`wrynose/linux-firmware`), meta-selinux, meta-updater |
| `oeros-wrynose-jazzy-qualcomm` | IQ-9075, IQ-8275 (QIR SDK) | as above + meta-qcom-robotics-sdk, with meta-ros2-jazzy: the SDK is built against ROS 2 Jazzy and its bbappends and `domain-bridge` do not exist for Lyrical |
| `oeros-wrynose-lyrical-ti` | AM62A, AM68, AM69 | meta-arm, meta-ti (bsp, extras, test), meta-arago (distro, extras), meta-tisdk/meta-ti-foundational, meta-edgeai |
| `oeros-wrynose-lyrical-intel` | intel-corei7-64 | meta-intel, meta-openvino, meta-clang-revival (meta-intel's onednn and intel-compute-runtime dynamic layers) |
| `oeros-wrynose-lyrical-amd` | KR260, KV260, KD240, VEK280, VEK385 (+ multidomain) | see `docs/amd-xilinx.md`; includes meta-zephyr and meta-amd-zephyr for the multidomain RPU firmware |
| `oeros-wrynose-jazzy` (hand-written) | intel-corei7-64 + Robotics AI Suite | meta-intel, meta-openvino, meta-ros2-jazzy |

Common set: oe-core, meta-openembedded (filesystems, gnome, initramfs,
multimedia, networking, oe, perl, python, webserver, xfce), meta-clang,
meta-intel-realsense, meta-oeros, meta-tensorflow-lite, meta-onnxruntime,
meta-python-ai, meta-qt6, meta-ros (common, ros2, ros2-lyrical),
meta-virtualization, meta-security (+ meta-tpm), meta-zenoh.

The vendor layers in **bold** below were missing from the old single
config even though the vendor layers declare them in `LAYERDEPENDS`, so
those vendors could not have parsed: meta-qcom needs
`lts-linux-firmware-mixin`; meta-qcom-distro needs `selinux`, `sota`
(meta-updater) and `tpm-layer`; meta-imx-sdk needs `freescale-distro`,
which needs `yocto`; meta-edgeai needs `meta-ti-test`,
`meta-arago-distro`, `meta-arago-extras` and `meta-ti-foundational`.

Two more layers are needed for the vendors' inference runtimes to parse,
not just their BSPs:

- **meta-freescale-ml** (NXP): holds the base `tensorflow-lite`, delegate,
  `tim-vx` and `nnstreamer` recipes that meta-imx-ml only bbappends.
  Without it those bbappends dangle. NXP's own `imx-setup-release.sh`
  adds it.
- **meta-ai** (Qualcomm, collection `ai`): meta-qcom only parses its
  `dynamic-layers/ai` (the `onnxruntime-qnn` plugin EP) when this layer is
  present, as in meta-qcom's `ci/qcom-distro.yml`. At priority 10 its
  `onnxruntime` 1.26.0 replaces meta-onnxruntime's on Qualcomm builds;
  that build has **no Python bindings**, so `import onnxruntime` is not
  available on Qualcomm images. meta-onnxruntime's pinned 1.22.0 predates
  the ORT plugin-EP API that `onnxruntime-qnn` 2.x needs.

Which `onnxruntime` each vendor actually builds (highest layer priority
wins, and every vendor EP is compiled into that recipe, not shipped as a
separate package):

| Vendor | `onnxruntime` from | Version | EPs |
|---|---|---|---|
| generic, TI, Intel, AMD | meta-onnxruntime (priority 6) | 1.22.0 | CPU only (TI: verify whether meta-edgeai overrides it) |
| Nvidia | meta-tegra-community (priority 20) | 1.29.1 | CUDA, TensorRT |
| NXP | meta-imx-ml (priority 9) | 1.24.3 | VSINPU (i.MX 8), Neutron (i.MX 95) |
| Qualcomm | meta-ai (priority 10) + `onnxruntime-qnn` plugin | 1.26.0 + 2.4.0 | CPU + QNN (plugin EP) |

## Proprietary opt-in

No vendor `.inc` accepts a license on the user's behalf any more. Each
vendor with gated content has a fragment, enabled after `bitbake-setup
init` with `bitbake-config-build enable-fragment oeros/<name>`:

| Fragment | What it sets | What it unlocks |
|---|---|---|
| `oeros/nvidia-proprietary` | `LICENSE_FLAGS_ACCEPTED += commercial`, `MACHINE_FEATURES += edgeai-nvidia-proprietary` | All of `packagegroup-oeros-edgeai-tegra` (cuDNN, TensorRT, nv GStreamer plugins, DeepStream, Isaac ROS). meta-tegra itself declares no `LICENSE_FLAGS`, so the old `commercial_tegra` flag in the `.inc` matched nothing. |
| `oeros/qcom-proprietary` | `LICENSE_FLAGS_ACCEPTED += commercial`, `MACHINE_FEATURES += edgeai-qcom-proprietary` | `-runtime`/`-dev` (QAIRT, FastCV, Hexagon binaries) and `packagegroup-oss-with-prop-deps`. The open QIR SDK groups stay available without it. |
| `oeros/nxp-proprietary` | requires meta-freescale's `eula/accept-fsl-eula` fragment (`ACCEPT_FSL_EULA = "1"`), `LICENSE_FLAGS_ACCEPTED += commercial` | **Required to build any i.MX image**: `fsl-eula-unpack` calls `bb.fatal()` for EULA-covered recipes, including the boot firmware. |
| `oeros/amd-proprietary` | see `docs/amd-xilinx.md` | VCU/VCU2 firmware, libmali, Kria PL firmware (starter kits, motor control, TSN, KV260 camera), AP1302 ISP firmware |

TI and Intel have no fragment: neither meta-ti/meta-edgeai nor
meta-intel/meta-openvino declares `LICENSE_FLAGS` or an EULA gate.


Selecting a `oeros/machine-<board>` option in the `machine` one-of category is
self-contained: it sets `MACHINE`, pulls in the vendor `.inc`, sets
`ROS_DISTRO = "lyrical"`, and enables the `edgeai` distro feature + packagegroup.

## Qualcomm Intelligent Robotics SDK (`meta-qcom-robotics-sdk`)

Separate from (and not blocked like) the QIM SDK above: **QIR SDK**
(`meta-qcom-robotics-sdk`) has its own `wrynose` branch and is added on
this branch for its two officially-supported machines, `iq-9075-evk`
(QCS9100 family) and `iq-8275-evk` (QCS8300 family) — matching the boards
in the SDK's own `ci/*.yml` kas configs. Wired in as
`packagegroup-oeros-edgeai-qcom`'s new `-robotics` sub-package, gated on
an `edgeai-robotics-sdk` `MACHINE_FEATURE` those two machines' fragments
set (so it doesn't affect `qcs6490-rb3gen2-core-kit`/`qcs9100-ride-sx`,
which the SDK doesn't officially support).

Packagegroups consumed directly from `meta-qcom-robotics-sdk` (RDEPENDS,
not re-derived):

| Packagegroup | Contents |
|---|---|

- `qrb-ros-nn-inference` (the same package the original draft's
  hand-rolled `-ros` component guessed at) is real here, and depends on
  `qairt-sdk` + `tensorflow-lite` at build time — consistent with the
  `-runtime` packages already in `packagegroup-oeros-edgeai-qcom`.

  family in the MACHINE name so the old regex substring-matched them, but

- Full device/kernel bring-up (kas `linux-qcom-6.18.yml` etc.) wasn't
  cross-checked against `meta-qcom`'s own `iq-9075-evk.conf`/
  `iq-8275-evk.conf`; both machines already exist in `meta-qcom` itself
  (`recipes-bsp/packagegroups/packagegroup-iq-9075-evk.bb` etc.), so the
  robotics SDK layers on top of an already-working MACHINE rather than
  introducing a new one.

## Intel Robotics AI Suite (`packagegroup-oeros-robotics-ai-suite`)

Source: `open-edge-platform/edge-ai-suites`, path `robotics-ai-suite/`
(a large monorepo bundling many unrelated Intel product suites —
robotics, education, manufacturing, healthcare, etc. — as one repo).
**No Yocto layer exists for this suite anywhere** (checked the
`open-edge-platform` and `intel` GitHub orgs, the Yocto Project Layer
Index, and GitHub-wide code search); its own release engineering targets
Ubuntu/APT (`.deb`s built by Docker + per-component Makefiles). This is
greenfield recipe work, in a new `dynamic-layers/openvino/recipes-robotics-ai-suite/`
directory. It is a dynamic layer keyed on meta-openvino (`openvino`):
`yolo` DEPENDS on `openvino-inference-engine`, and none of these recipes sets
`COMPATIBLE_MACHINE`, so as plain `recipes-*` they were parsed in every config
and `yocto-check-layer`'s `test_world` failed with "Nothing PROVIDES
'openvino-inference-engine'" on the base config.

**Recipes created with `recipetool create` + manual ROS-ification**, per
project convention: `recipetool` gets `SRC_URI`/`SRCREV`/a first-pass
license scan right, then each recipe was hand-corrected to use the
`ros_distro_${ROS_DISTRO}` / `ros_component` / `ros_${ROS_BUILD_TYPE}`
pattern (recipetool has no ROS-specific knowledge and defaults to plain
`inherit cmake`), with `DEPENDS`/`RDEPENDS` fixed to the real meta-ros
package names (recipetool's CMake `find_package()` guesses are
approximate) and `LICENSE`/`LIC_FILES_CHKSUM` cross-checked against each
component's actual `REUSE.toml`/`LICENSES/` directory.

**Why a separate Jazzy config.** The suite officially validates ROS 2
Jazzy Jalisco / Ubuntu 24.04; this whole distro's default is ROS 2
"lyrical" (newer than Jazzy in meta-ros's lineage — `navigation2` is
1.5.1 on lyrical vs. 1.3.13 on jazzy, a real version gap). Rather than
build the suite against an unverified newer ROS_DISTRO, this integration
forks to Jazzy — but `bitbake-setup` configs share ONE `bb-layers` list
across every machine option in a config file, so `meta-ros/meta-ros2-jazzy`
cannot simply be added alongside `meta-ros/meta-ros2-lyrical` in
`oeros-wrynose-lyrical.conf.json` without both ROS-distro package sets
(near-certainly colliding on recipe names like `navigation2`, `rclcpp`)
landing in the same `BBLAYERS` for every machine in that config, not just
Intel's. The fix is the new, separate `oeros-wrynose-jazzy.conf.json`,
scoped to just this Intel path — the first concrete instance of the
"Recommended new OE configuration templates" idea already in this file.
Its `oeros/machine-intel-corei7-64-robotics-ai-suite` fragment is also
where the `edgeai-robotics-ai-suite` `MACHINE_FEATURE` gets set (fragment-
level gating, same pattern as the Qualcomm QIR SDK above) — the existing
lyrical `machine-intel-corei7-64.conf` is untouched.

**A note on `recipetool` and this specific monorepo**: `edge-ai-suites`
has `.gitmodules` at its root, so `recipetool` auto-upgrades every fetch
to `gitsm://` and recursively clones *all* submodules repo-wide —
including entirely unrelated products bundled in the same monorepo (e.g.
`education-ai-suite/ai-teaching-assistant/.../datumaro`,
`pipelines/gr00t-n1d7-ov/isaac-gr00t/.../LIBERO`, `.../ManiSkill2_real2sim`
several directories deep in an unrelated humanoid-robot-learning pipeline).
`--src-subdir` only scopes where `recipetool` *looks* for build files
afterward, not what it fetches. This made `object-detection-tutorial`'s
and `segmentation-realsense-tutorial`'s `recipetool create` runs balloon
to 10+ minutes fetching gigabytes of irrelevant ML framework submodules,
and one run had to be killed (own local subprocess only) after it started
cloning `LIBERO`; `segmentation-realsense-tutorial` was hand-written
instead once its trivial `package.xml` (zero dependencies) was already
known. Worth keeping in mind for any future component pulled from this
same monorepo.

## Recommended new OE configuration templates

The single `oeros-wrynose-lyrical` configuration now unconditionally lists
every vendor's BSP/tools layers in `bb-layers` (Nvidia, NXP, Qualcomm, TI,
Intel, and — on the follow-up branch — AMD) even though a given build only
ever uses one vendor's `MACHINE`. That's a real cost: every vendor layer's
own recipes still get parsed on every build regardless of which
`oeros/machine-*` option is picked. Recommend splitting into focused,
per-vendor `bitbake-setup` configuration templates once this stabilizes,
e.g.:

- `oeros-wrynose-lyrical-nvidia.conf.json`
- `oeros-wrynose-lyrical-nxp.conf.json`
- `oeros-wrynose-lyrical-qualcomm.conf.json`
- `oeros-wrynose-lyrical-ti.conf.json`
- `oeros-wrynose-lyrical-intel.conf.json`
- `oeros-wrynose-lyrical-amd.conf.json` — **exists** (`feature/edgeai-v3`); forced early because meta-xilinx-multimedia overrides GStreamer's PREFERRED_VERSION from its layer.conf

Each would set `"extends": "oeros-wrynose-lyrical"` (mirroring how the
original `oeros-edgeai-setup.json` draft used `"extends": "oeros-base"`)
and add only that vendor's `bb-layers`, keeping the base config's
`oeros/machine-*` options but scoped to just its own boards. This is the
concrete mechanism for "selectively enable functionality from the vendor
layers" that parse-time bloat in the single monolithic config works
against today.

## `oeros-inference-node`: options (open for discussion)

`packagegroup-oeros-edgeai-ros` RDEPENDS on `oeros-inference-node`,
described as "an ONNX Runtime node in this layer whose execution provider
is selected at runtime by `OEROS_EDGEAI_VENDOR`". No recipe exists yet.
The name is used like a capability ("an inference node for this board"),
so a provides-style dependency fits better than one hard-coded recipe.
The options:

1. **One real recipe, EP chosen at runtime.** A single ROS 2 node (C++ or
   Python) on ONNX Runtime publishing `vision_msgs`. At build time this
   layer writes `OEROS_EDGEAI_VENDOR` into a small config file (for example
   `/etc/oeros/edgeai.conf`); at start-up the node maps it to an EP
   (`openvino`, `tensorrt`, `qnn`, `vsinpu`, `tidl`, `vitisai`) and falls
   back to the CPU EP if that EP isn't in the build.
   *For:* one API, one codebase, works today on CPU everywhere.
   *Against:* most vendor EPs aren't packaged on wrynose yet (see
   "Things to verify"), so most boards would run on the CPU until they are,
   and it ignores vendors' own, better-optimized ROS nodes.
2. **Virtual runtime provider.** Keep the name as a virtual: each
   implementation declares `RPROVIDES:${PN} = "oeros-inference-node"`, and
   each vendor `.inc` picks one with
   `PREFERRED_RPROVIDER_oeros-inference-node = "..."`. Candidates already
   exist: `qrb-ros-nn-inference` (Qualcomm QIR SDK), Isaac ROS
   `isaac-ros-dnn-inference` (Nvidia, once packaged), TI's edgeai ROS nodes,
   and Oeros' own ORT node for everyone else.
   *For:* each board gets the vendor-tuned node; no single codebase to
   maintain across six accelerators.
   *Against:* the implementations have different topics, parameters and
   model formats, so "the inference node" is only interchangeable at the
   package level, not at the ROS interface level, unless Oeros defines a
   contract (topics + `vision_msgs` types + launch arguments) and wraps
   each one with a launch file to meet it.
3. **Hybrid (recommended).** Option 2's virtual, with option 1's ORT node as
   the default provider (`oeros-inference-node-ort`, CPU EP plus whatever
   vendor EP is present), and a documented Oeros interface contract.
   Vendor nodes are opted in per board with `PREFERRED_RPROVIDER` once a
   thin launch wrapper maps them onto the contract. This gets every board a
   working node now and lets vendor nodes replace it one at a time.

Whichever option is chosen, the `OEROS_EDGEAI_VENDOR` value has to reach
the target (it is only a BitBake variable today), so that part is needed
in every option.
