# Oeros on AMD/Xilinx adaptive SoCs (wrynose, rel-v2026.2)

This branch (`feature/edgeai-v3`, forked from
`feature/edgeai-intel-robotics-ai-suite`) adds AMD Kria and Versal AI Edge
boards to Oeros. It supersedes the "Deferred to
`feature/edgeai-amd-xilinx-lag`" note in `docs/edgeai.md`: as of AMD's
**rel-v2026.2** release, the AMD board layers declare
`LAYERSERIES_COMPAT = "wrynose"`, so the boards no longer need a lagging
branch.

Everything below was checked against shallow clones of each repository's
`rel-v2026.2` branch (checked 2026-11-13), not against documentation.

## How to build

The AMD boards live in their **own** bitbake-setup configuration,
`conf/registry/configurations/oeros-wrynose-lyrical-amd.conf.json`, not in
`oeros-wrynose-lyrical`:

```
bitbake-setup init \
    meta-oeros/conf/registry/configurations/oeros-wrynose-lyrical-amd.conf.json \
    oeros-wrynose-lyrical-amd distro/oeros oeros/machine-k26-smk-kr-sdt
```

Why a separate config: `meta-xilinx-multimedia/conf/layer.conf` sets
`PREFERRED_VERSION_gstreamer1.0*` to AMD's `1.28.2+amd` fork from the layer
itself. bitbake-setup shares one `bb-layers` list across every machine option
in a config, so adding the AMD layers to the shared lyrical config would swap
GStreamer for the Jetson, i.MX, Qualcomm, TI and Intel boards too. Every
vendor now has its own config (see "Configurations" in `docs/edgeai.md`),
all generated by `scripts/gen-registry-configs.py`.

The AMD machines use AMD's **System Device Tree (SDT)** flow: the machine
`.conf` fetches the board's SDT bundle from `edf.amd.com` and builds FSBL and
PMU firmware from source through BitBake multiconfig. No Vivado/Vitis install
and no `meta-xilinx-tools` are needed.

## Proprietary opt-in (`oeros/amd-proprietary`)

The default AMD build is **open source only**. Unlike
`oeros-edgeai-qcom.inc` and `oeros-edgeai-tegra.inc`, the AMD `.inc` does not
touch `LICENSE_FLAGS_ACCEPTED`. To opt in, enable the fragment after
`bitbake-setup init`:

```
bitbake-config-build enable-fragment oeros/amd-proprietary
```

| What the fragment sets | What it unlocks | License |
|---|---|---|
| `LICENSE_FLAGS_ACCEPTED += "xilinx"` | `pmu-rom-native`, needed only to boot a ZynqMP image under QEMU. It also silences the `xilinx-vars.bbclass` warning. | Proprietary (`LICENSE_FLAGS = "xilinx"`) |
| `LICENSE_FLAGS_ACCEPTED += "commercial"` | `gstreamer1.0-omx`, `-libav` and `-plugins-ugly` from meta-xilinx-multimedia, which the VCU OpenMAX pipeline uses | `LICENSE_FLAGS = "commercial"` |
| `DISTRO_FEATURES += "libmali"` | `libmali-xlnx` instead of Mesa. On Kria (Mali-400) the open default is Lima. On VEK385 (Mali-G78AE) Mesa has no driver, so without this the GPU is unused and rendering falls back to the CPU. | Proprietary |
| (same feature, Kria apps) | `packagegroup-oeros-kria-apps-proprietary`: the PL designs the Kria apps load (`kd240-motor-ctrl-qei-fw` on KD240, `kr260-tsn-rs485pmod-fw` on KR260, `kv260-bist-fw` on KV260) and the onsemi `ap1302-firmware` ISP firmware on KV260 | `Advanced-Micro-Devices-Xilinx-binaries`; `Firmware-AP1302` |
| `MACHINE_FEATURES += "edgeai-amd-proprietary"` | `packagegroup-oeros-edgeai-xilinx-proprietary`. With the `vcu` feature (K26: KR260/KV260) it adds `kernel-module-vcu`, `vcu-firmware`, `libvcu-omxil`, `gst-plugins-vcu` and `gstreamer1.0-omx`. With `vcu2` (VEK385) it adds the VCU2 equivalents. On Kria it adds the `k26-starter-kits` or `k24-starter-kits` PL firmware bundle. These are listed directly rather than through `packagegroup-kria`, which also needs `packagegroup-security-tpm2` from meta-security. | `vcu-firmware`, `vcu2-firmware`: Proprietary. `kria-base-firmware`: Proprietary & GPL-2.0-only. |

**Vitis AI** has a separate, documented hook: `MACHINE_FEATURES +=
"edgeai-vitis-ai"` adds `packagegroup-oeros-edgeai-xilinx-vitis-ai` (`vart`,
`vart-ml`, `vart-x`). **No wrynose layer can satisfy it today.** No fragment
sets it, and nothing turns it on by default:

- `meta-vitis` on rel-v2026.2 (it was `meta-vitis-ai`; GitHub serves the
  same commit under both names) now contains only `packagegroup-vitis-aiml`
  (open-source build dependencies) and `h5pp`. The Vitis AI 3.5
  VART/DPU recipes are already gone by rel-v2025.1.
- Vitis AI **6.3** ([amd/Vitis-AI](https://github.com/amd/Vitis-AI))
  supports only Versal AI Edge (VEK280) and Versal AI Edge Gen 2 (VEK385).
  Its Yocto recipes sit inside each board's reference design
  (`versal_ve/reference_design/vek280/sw/yocto/meta-vitis-ai`). That layer
  declares `LAYERSERIES_COMPAT = "scarthgap"` (EDF 2026.1), and `vart`,
  `vart-ml`, `vart-x`, `hip`, `pvt` and `cert-ve2` are `LICENSE = "CLOSED"`.
- Kria/ZynqMP DPU is not supported by Vitis AI 6.x at all.

### Not wrynose, so not in the table

- `meta-xilinx-tools` (`master`: `LAYERSERIES_COMPAT = "styhead walnascar"`;
  `rel-v2026.2-scarthgap`: scarthgap). Its `zcu102-zynqmp`,
  `vek280-versal` and similar XSCT-based machines are superseded by the SDT
  machines above.
- `meta-amd-edf-bsp` is wrynose, but its machines are the EDF "common"
  machines (`amd-cortexa53-mali-common`, `amd-cortexa78-mali-common`, ...),
  one image per CPU class, plus Alveo/Embedded+ management controllers. The
  generic common machines are an alternative to per-board machines. Vitis AI
  6.3's VEK385 build uses `amd-cortexa78-mali-common`. I did not adopt them
  because the other vendors in Oeros all use per-board machines.

## AMD Kria robotics apps (`dynamic-layers/xilinx/recipes-kria-apps/`)

Source: [Xilinx/meta-kria-apps](https://github.com/Xilinx/meta-kria-apps)
`main` (MIT, `LAYERSERIES_COMPAT = "scarthgap"`). Unlike the Intel suite,
AMD already wrote proper ROS-ified recipes, so the port is small. Each
recipe header lists its changes; in short: `S` moves from
`${WORKDIR}/git` to `${UNPACKDIR}/${BP}` (wrynose unpack layout),
`ros_distro_jazzy` becomes `ros_distro_${ROS_DISTRO}`, and every recipe is
`COMPATIBLE_MACHINE` Kria only.

| Recipe | What | Board | License |
|---|---|---|---|
| `ros-tsn-pubsub_0.3.0` | ROS 2 talker/listener + FastRTPS profiles for the multi-node-over-TSN demo | KR260, KD240 | MIT |
| `foc-motor-ctrl_0.6` | FOC motor-control library, pybind11 binding, CANopen server (`fmc_canopen`), Bokeh dashboard | KD240 | MIT |
| `kria-motor-control_0.6` | ros2_canopen / ros2_control client that drives the KD240 motor server over CAN | KR260 | MIT |
| `motor-control-iio-modules_0.3` | Out-of-tree IIO drivers for the KD240 motor-control PL IP | KD240 | GPL-2.0-only |
| `kd240-motor-ctrl-qei-fw_1.2`, `kr260-tsn-rs485pmod-fw_1.2` | PL designs (bitstream + DT overlay) | KD240, KR260 | AMD binaries, **opt-in** |
| `ar1335-module_0.1` | Out-of-tree AR1335 sensor V4L2 driver | KV260 | GPL-2.0-only |
| `ap1302-firmware_1.0` | onsemi AP1302 ISP firmware | KV260 | Firmware-AP1302, **opt-in** |
| `kv260-bist-fw_1.2` | PL design with the AR1335/AP1302 MIPI capture pipeline + VCU | KV260 | AMD binaries, **opt-in** |

One real change: `velocity-controllers` was dropped from
`kria-motor-control`'s exec deps, since meta-ros2-lyrical has no recipe
for it; `forward-command-controller` covers velocity commands.

`packagegroup-oeros-kria-apps` selects per board (`-tsn`, `-motor-control`
on KD240, `-motor-control-client` on KR260, `-camera` on KV260, and
`-proprietary`). `packagegroup-oeros-edgeai-xilinx-kria` pulls it in.
Without the opt-in the apps install, but there is no PL design for them to
talk to.

**KV260 camera.** The KV260 basic camera kit is an AR1335 sensor behind an
onsemi AP1302 ISP, MIPI CSI-2 into the PL. Open part: `ar1335-module`,
`v4l-utils`, `media-ctl`, `yavta`; ROS 2 capture comes from `v4l2-camera` and
`gscam` in `packagegroup-oeros-edgeai-ros`. The capture pipeline itself is
the `kv260-bist` PL design plus AP1302 firmware (both opt-in). That design
also pulls the in-tree `kernel-module-ap1302` and `kernel-module-xlnx-vcu`.
Their presence in linux-xlnx's config is taken from meta-kria-apps and is
not verified here.

## OpenAMP multidomain machines

`oeros/machine-{k26-smk-kr-sdt,k26-smk-kv-sdt,k24-smk-kd-sdt,versal-vek280,versal-2ve-2vm-vek385-revb}-multidomain`
use AMD's AMP machines: Linux on the APU plus FreeRTOS, bare-metal or
Zephyr on the Cortex-R5F (R52 on VEK385), built through multiconfig and
connected over RPMsg. The fragments set `DISTRO_FEATURES += "openamp"` and
`MACHINE_FEATURES += "edgeai-openamp"`, which adds
`packagegroup-oeros-edgeai-xilinx-openamp` (meta-xilinx's
`packagegroup-openamp`, with libmetal, open-amp, rpmsg modules and demos).
On KR260/KV260 it also adds meta-kria's prebuilt Cortex-R5 Zephyr demo
firmware. AMD's VEK280/VEK385 demo firmware recipes are only compatible
with the EDF "common" machines, so none is added there. AMD ships no
KD240 demo firmware.

## Vitis AI on wrynose: effort and impact (port held)

**What a port involves.** Vitis AI 6.3 ships Yocto content only inside
[amd/Vitis-AI](https://github.com/amd/Vitis-AI)'s per-board reference
designs. These are scarthgap (EDF 2026.1) layers, not a published layer:

| Reference design | Recipes | bbappends | Patches | Notes |
|---|---|---|---|---|
| VEK280 (`versal_ve/.../vek280/sw/yocto`) | 6 | 4 | 0 | `vart`, `vartml-sw`, `x-plus-ml`, its own `onnxruntime_1.18.1`, `mipso-udev`, plus a `meta-vek280` BSP |
| VEK385 Rev B (`versal_2ve/.../vek385/rev-b/sw/yocto`) | 28 | 16 | 34 | `vart-ml`, `vart-x`, `cert-ve2`, `pvt` (CLOSED), VVAS, `amdxdna`, `amdrnpu` NPU firmware, a pinned `protobuf_3.21.12`, `ryzenai-wheels` (installs prebuilt `onnxruntime_vitisai`/`flexmlrt` wheels from `pypi.amd.com`), bbappends on linux-xlnx, xrt, zocl, ai-engine-driver, xen, u-boot, device-tree, bootbin |

Estimated effort (my estimate, not measured):
- **VEK280: small to medium, about 1 to 2 weeks.** The usual
  scarthgap-to-wrynose changes (`S`/`UNPACKDIR`, `LAYERSERIES_COMPAT`,
  QA). The real work is replacing its private `onnxruntime_1.18.1` with
  the Vitis AI EP on top of meta-onnxruntime's 1.31, or carrying both
  under different names.
- **VEK385: medium to large, about 3 to 6 weeks.** The 34 patches and 16
  bbappends target AMD's 2026.1 EDF versions of linux-xlnx, xrt, zocl and
  ai-engine-driver. Every one has to be rebased onto rel-v2026.2
  (ai-engine-driver alone moves from 3.8 to 4.0). The pinned protobuf
  3.21 conflicts with wrynose's protobuf, and `ryzenai-wheels`
  downloads binaries at build time. That fails BitBake's offline/mirror
  model and needs a proper fetcher.
- **Both: licensing.** `vart`, `vart-ml`, `vart-x`, `cert-ve2` and `pvt`
  are `LICENSE = "CLOSED"`. Oeros could at most carry recipes that fetch
  them behind `oeros/amd-proprietary` (as `-vitis-ai` is set up for).
  Redistributing the binaries needs AMD's permission.
- **Ongoing.** AMD re-cuts these per Vitis AI release (6.2 to 6.3 already
  moved the VEK385 tree), so a port is a recurring rebase, not a one-off,
  until AMD publishes a versioned wrynose layer.

**Impact of not porting.**
- **Kria (KR260, KV260, KD240): none, relative to anything available
  today.** Vitis AI 6.x does not support Zynq UltraScale+ or its DPU at all;
  the last release covering Kria was Vitis AI 3.5, whose recipes were
  already gone from meta-vitis by rel-v2025.1 (the oldest branch I checked). Porting 6.3 would not help Kria. On Kria,
  inference runs on the Cortex-A53 CPU (ONNX Runtime/TFLite from
  packagegroup-oeros-edgeai-core), or in the PL through
  XRT with HLS / Vitis Libraries kernels loaded by `dfx-mgr`/`xmutil`.
  Both work without Vitis AI. Bringing back a DPU on Kria would mean
  maintaining the Vitis AI 3.5 stack (VART 3.5, the DPUCZDX8G PL design and
  the xmodel compiler) out of tree against wrynose, which AMD no longer
  supports. That is larger than either port above.
- **VEK280/VEK385: large.** Their AIE-ML/AIE-MLv2 arrays are the point of
  the boards, and without VART they sit idle for ML (XRT and the AIE driver
  are there, but nothing compiles models for them). They remain good
  Linux/ROS 2/real-time targets, but not Edge AI targets, until the port
  happens or AMD ships a wrynose layer.
- **Parity.** AMD stays the one vendor in Oeros without an accelerated
  inference runtime (see the comparison table).
